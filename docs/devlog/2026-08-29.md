## 08:23 〜 v1 ディレクトリ構成の骨組みと migrate.ts の実装

### やったこと
- SPEC.md のディレクトリ構成に沿って `package.json` / `tsconfig.json` / `migrations/` / `src/server/` / `tests/server/` を新規作成
- `migrations/001_init.sql` に SPEC.md のデータモデル(`pages`, `page_revisions`, `links`, `pages_fts`(FTS5 trigram), `schema_version`)をそのまま定義
- `src/server/migrate.ts` を実装。`schema_version` テーブルの有無 → 適用済みバージョン集合を求め、未適用の `migrations/*.sql` を番号順・1ファイル1トランザクションで適用し、成功ごとに `schema_version` へ番号を記録する
- `tests/server/migrate.test.ts` で以下を確認
  - 空 DB に `001_init.sql` を適用すると SPEC 通りの表一式ができる
  - 一時ディレクトリに複数マイグレーションを用意して「空 DB からの全適用」「途中(001 だけ適用済み)から再開して 002 が追加された後の再開」「同じ migrate() を複数回呼んでも二重適用にならない」を検証
  - FTS5 の shadow table(`pages_fts_*`)や `sqlite_sequence` はマイグレーションが直接定義した表ではないため、テーブル一覧の比較から除外
- `bun install` → `bun test` / `bun run typecheck` が通ることを確認
- 実装前に ADR-0001(Bun/bun:sqlite/React 選定)・ADR-0002(番号付き SQL + schema_version によるマイグレーション方式)を Accepted で起票(SPEC.md にすでにある決定の遡及ドキュメント化)

### 詰まった点・気づき
- `schema_version` テーブル自体を `001_init.sql` の中で作る設計なので、`migrate.ts` は「テーブルが無ければ未適用 0 件」という形でブートストラップする必要があった。専用の管理テーブルを別に持たない分、この分岐が唯一の複雑ポイント
- FTS5(`tokenize='trigram'`)は内部的に `_data` / `_idx` / `_docsize` / `_config` の shadow table を作る。マイグレーションのテスト側でテーブル一覧を突き合わせるときはこれらを除外しないと壊れる
- `server.ts` / `db.ts` / `pages.ts` などディレクトリ構成上の他のファイルは、今回のタスク(001_init.sql と migrate.ts)の範囲外として未着手のまま残した

### 関連ADR / コミット
- ADR-0001, ADR-0002

### 詰まった点・気づき

## 11:52 〜 src/server/pages.ts の実装(CRUD + リビジョン + 論理削除)

### やったこと
- 実装前に ADR-0003(10分ルールによるリビジョンの積み方)を Accepted で起票
- `ulid` を依存に追加(CLAUDE.md の許可リスト内。ページ ID 用)
- `src/server/pages.ts` を実装
  - `listPages` / `getPage`: `deleted_at IS NULL` で絞る。一覧は更新日時降順
  - `getByTitle`: 未存在なら ULID を振って空ページ(`lines = [title]`)を作成。削除済み同名ページがある場合は、内容をリビジョンに退避してから同じ行を空ページとして蘇生(title UNIQUE + 物理削除禁止のため新規 INSERT はできない)
  - `save`: 毎回 pages・links・pages_fts を更新し、リビジョンは「内容が直前と異なる かつ(初回 / 10分経過 / 離脱時)」のときだけ積む。判定はすべて save() 内(CLAUDE.md)
  - 改名時は `links.to_title` で旧タイトルへのリンク元を探し、本文の `[旧title]` を `[新title]` に置換して links / fts を追随させる
  - `deletePage`: `deleted_at` を立てるだけ
  - `listRevisions`(json_array_length で行数算出・新しい順)/ `getRevision` / `restore`(現在の状態を積む → 上書き)
- `pages_fts` の再生成も pages.ts に置いた(body は `lines.join("\n")`)
- テスト18件追加: 作成・蘇生・リビジョン判定4パターン・改名伝播・論理削除・restore の順序など

### 詰まった点・気づき
- 削除済みページと同名の新規作成は SPEC に記載がない穴だった。title UNIQUE と物理削除禁止が両立する以上 INSERT はできないので、「旧内容をリビジョンに退避 → 同じ行を空にして蘇生」とした。削除前の本文は履歴から辿れる
- 改名伝播で他ページの `updated` は変えないことにした(改名の巻き添えで一覧の並び順が動くのは不自然)。また SPEC どおり `[旧title]` のみ置換し、`#旧title` 形式は置換しない(その分 links に旧タイトルへのリンクが残るが、リンク解決時に未存在ページ扱いになるだけ)
- 時刻は全関数で `now` 引数として注入可能にした。10分ルールのテストが実時間に依存せず書ける

### 関連ADR / コミット
- ADR-0003

## 14:04 〜 src/server/search.ts の実装

### やったこと
- `src/server/search.ts` を実装
  - クエリのコードポイント数(`[...q].length`)が3以上なら FTS5 `MATCH`、それ未満は `LIKE` フォールバック(CLAUDE.md の分岐そのまま)
  - FTS5 に渡すクエリは `"..."` で囲み、内部の `"` を `""` にエスケープ。ユーザ入力が MATCH 構文として解釈されない
  - LIKE 側は `%` `_` `\` を `ESCAPE '\'` でエスケープし、ワイルドカード注入を防ぐ
  - どちらの経路も `deleted_at IS NULL` で絞る。並びは FTS が rank、LIKE は更新日時降順
- LIKE の本文マッチは `pages.lines`(JSON文字列)ではなく `pages_fts.body`(素のテキスト)に当てた。JSON のエスケープ(`\"` など)が部分一致に混ざるのを避けるため
- テスト10件: 3文字境界、サロゲートペア(𩸽𩸽 = UTF-16 では length 4)、日本語 FTS/LIKE、`"` を含むクエリ、`%`/`_` の非ワイルドカード化、削除済み除外、タイトル・本文両ヒット

### 詰まった点・気づき
- 2文字クエリで `"` そのものを本文検索するケースは、`pages_fts.body` に当てる方式にしたことで JSON エスケープ問題ごと消えた。`lines` に LIKE していたら `\"` に阻まれて当たらなかった
- FTS5 の仮想テーブルは JOIN 時にエイリアスを付けると `MATCH` の左辺に使えるか処理系依存で怪しいので、`pages_fts` をテーブル名のまま参照した

### 関連ADR / コミット
- なし(trigram + LIKE フォールバック方式は ADR-0001/SPEC.md 記載の決定の実装)

## src/server/upload.ts の実装(画像の sha256 保存)

### やったこと
- `src/server/upload.ts` を実装
  - `saveImage(bytes, contentType, dir)`: 内容の sha256 をファイル名にして `data/images/<hash>.<ext>` に保存し、`/files/<hash>.<ext>` の相対 URL を返す(SPEC.md。ホスト名は本文に入れない)
  - 拡張子は Content-Type から決定(png / jpg / gif / webp / svg)。未知のタイプは throw して routes.ts 側でエラー応答にする想定
  - 同一内容は同名ファイルに収束するので、既存チェックして二重書き込みしない
  - `resolveImagePath(name, dir)`: `GET /files/:name` 配信用。`[0-9a-f]{64}\.既知拡張子` に一致する名前だけパスを返し、パストラバーサルを形式で締め出す
- テスト: 既知の sha256 値("hello")での保存・URL・内容一致、重複保存の収束、jpeg→.jpg、未対応タイプの reject、トラバーサル・不正名の null

### 詰まった点・気づき
- 配信側の安全性はパス正規化ではなく「名前の形式チェック」に寄せた。ハッシュ命名のおかげで正当なファイル名の全集合が正規表現1本で書けるので、`..` や `/` の混入をケース列挙で防ぐより堅い
- ハッシュ計算は `Bun.CryptoHasher`(server 専用モジュールなので Bun API 依存で問題ない)
