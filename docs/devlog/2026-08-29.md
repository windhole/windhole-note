## 08:23 〜 v1 ディレクトリ構成の骨組みと migrate.ts の実装

### やったこと
- SPEC.md のディレクトリ構成に沿って `package.json` / `tsconfig.json` / `migrations/` / `src/server/` / `tests/server/` を新規作成
- `migrations/001_init.sql` に SPEC.md のデータモデル(`pages`, `page_revisions`, `links`, `pages_fts`(FTS5 trigram), `schema_version`)をそのまま定義
- `src/server/migrate.ts` を実装。`schema_version` テーブルの有無 → 適用済みバージョン集合を求め、未適用の `migrations/*.sql` を番号順・1ファイル1トランザクションで適用し、成功ごとに `schema_version` へ番号を記録する
- `tests/server/migrate.test.ts` で以下を確認
  - 空 DB に `001_init.sql` を適用すると SPEC 通りの表一式ができる
  - 一時ディレクトリに複数マイグレーションを用意して「空 DB からの全適用」「途中(001 だけ適用済み)から再開して 002 が追加された後の再開」「同じ migrate() を複数回呼んでも二重適用にならない」を検証
  - FTS5 の shadow table(`pages_fts_*`)や `sqlite_sequence` はマイグレーションが直接定義した表ではないため、テーブル一覧の比較から除外
- `bun install` → `bun test` / `bun run typecheck` が通ることを確認
- 実装前に ADR-0001(Bun/bun:sqlite/React 選定)・ADR-0002(番号付き SQL + schema_version によるマイグレーション方式)を Accepted で起票(SPEC.md にすでにある決定の遡及ドキュメント化)

### 詰まった点・気づき
- `schema_version` テーブル自体を `001_init.sql` の中で作る設計なので、`migrate.ts` は「テーブルが無ければ未適用 0 件」という形でブートストラップする必要があった。専用の管理テーブルを別に持たない分、この分岐が唯一の複雑ポイント
- FTS5(`tokenize='trigram'`)は内部的に `_data` / `_idx` / `_docsize` / `_config` の shadow table を作る。マイグレーションのテスト側でテーブル一覧を突き合わせるときはこれらを除外しないと壊れる
- `server.ts` / `db.ts` / `pages.ts` などディレクトリ構成上の他のファイルは、今回のタスク(001_init.sql と migrate.ts)の範囲外として未着手のまま残した

### 関連ADR / コミット
- ADR-0001, ADR-0002

## 10:14 〜 db.ts の実装

### やったこと
- `src/server/db.ts` を実装。`createDb(path)` が親ディレクトリを作成 → `new Database(path)` → `migrate(db)` を呼んで返すだけの薄いラッパー(デフォルトパスは `data/pages.db`)
- `tests/server/db.test.ts` で `:memory:` 指定時に migrate が実行されること、ファイルパス指定時に存在しない親ディレクトリを作ってから DB ファイルができることを確認
- `.gitignore` に `data/` を追加。`db.ts` のデフォルトパスが `data/pages.db` になったことで、CLAUDE.md の「`data/` 配下を git に入れない」ルールが実際に効くようにする抜け漏れだったので合わせて直した

### 詰まった点・気づき
- `createDb()` をモジュールトップレベルで即実行するシングルトンにすると、テストで `db.ts` を import しただけで実 DB ファイル(`data/pages.db`)ができてしまう。ファクトリ関数のままにして `server.ts`(未実装)側で一度だけ呼ぶ形にし、副作用を持たせないようにした

### 関連ADR / コミット
- なし(migrate.ts の薄いラッパーで新規の設計判断は無し)

## 10:22 〜 src/shared/syntax.ts の実装

### やったこと
- `src/shared/syntax.ts` に SPEC.md の記法(v1)表を一通り実装
  - `parseLine(line): Node[]`: `[タイトル]` / `#タグ` → `link`、`[* 強調]` → `bold`(`*` の数を level に)、`[https://...]` → `url`、`[/files/<hash>.png]` `[https://...png]` → `image`、`code:lang` 単独行 → `codeBlockStart`、それ以外は `text`
  - `indentOf(line): number`: 行頭の空白/タブの文字数(箇条書きのネスト深さ用)
- `tests/shared/syntax.test.ts` に記法ごとのパース結果テストを追加(空行、複数記法の混在、`[*not-bold]` のような非マッチケース、code:lang の誤検出防止など)
- `bun test` / `bun run typecheck` が通ることを確認

### 詰まった点・気づき
- CLAUDE.md の「1行を受け取ってノード配列を返す」という制約と、SPEC.md の「code:lang の次行以降、インデントされた行がコードブロック」という記法は素直には両立しない(コードブロックの範囲は複数行にまたがる状態を要る)。今回は `parseLine` は `code:lang` という開始マーカー行の検出だけを担当することにし、「次の行以降をコード行として扱うかどうか」の状態管理は呼び出し側(未実装の `links.ts` / `LineRenderer`)に委ねる設計にした
- `tsconfig.json` の `noUncheckedIndexedAccess` により、正規表現マッチ結果の添字アクセス(`match[1]` など)が `string | undefined` 扱いになりコンパイルエラーになった。マッチ済みで捕捉が保証されている箇所なので `!` で明示した

### 関連ADR / コミット
- なし(SPEC.md に記法表としてすでにある仕様の実装で、新規の設計判断は無し)

## 11:43 〜 src/shared/types.ts の実装

### やったこと
- `src/shared/types.ts` に `Page` / `Revision` 型を追加。SPEC.md の `pages` / `page_revisions` テーブル定義にフィールド名をそのまま合わせた(`deleted_at`, `page_id`, `saved_at` など snake_case のまま)
- `lines` は DB 上は `TEXT(JSON)` だが、型としては `JSON.parse` 済みの `string[]` として定義(DB との変換は今後 `pages.ts` が担う)
- 純粋な型定義のみで実行時ロジックが無いため専用のテストは追加せず、`bun test` / `bun run typecheck` が通ることのみ確認

### 詰まった点・気づき
- フィールド名を DB カラム名(snake_case)に合わせるか、TS の慣習である camelCase にするか迷った。`migrate.ts`/`db.ts` のテストがすでに `{ v: number }` のように SQL の結果をそのままの列名で受け取っている前例に合わせ、変換レイヤーを増やさない方針で snake_case のまま採用した

### 関連ADR / コミット
- なし(型定義のみで新規の設計判断は無し)
